## BUG FIXED: live-update de SSID quebrava o AP (commit `11555b1`, pushado) ✅

### Contexto
Herança de 2026-08-02: após mudar o SSID via app (Save Config), o AP anunciava o nome novo mas o roteamento morria (ping 100% loss, Chrome ERR_NETWORK_CHANGED, só DNS/captive probes chegavam ao device). Só reboot físico resolvia. Usuário pediu: "consegue consertar esse bug?"

### Root cause
`update_ap_ssid()` em `main/wifi_manager.c` chamava `esp_wifi_set_config(WIFI_IF_AP, ...)` **com o AP ativo e clientes conectados** → interface WiFi ficava em estado inconsistente (SSID trocado mas roteamento/DHCP morto).

### Fix aplicado
Sequência limpa (mesmo padrão que `disconnect_all_clients()` já usava):
1. `esp_wifi_stop()` — para o AP
2. `esp_wifi_set_config()` — aplica novo SSID
3. `esp_wifi_start()` — reinicia o AP limpo

netif e DHCP server sobrevivem ao stop/start. Novo log: `AP SSID updated (clean restart): <ssid>`.

### Validação em hardware (ESP32-C3 real, via app + phone)
| Teste | Antes | Depois |
|---|---|---|
| Ping 192.168.4.1 pós-troca de SSID | ❌ 100% loss | ✅ 0% loss |
| HTTP GET / (portal custom 313B) | ❌ travado | ✅ 200 OK |
| Captive redirect /generate_204 | ❌ | ✅ 302 → http://192.168.4.1/ |

Sequência: app → SSID "PromoBeacon-FIX" → Save Config → serial `AP SSID updated (clean restart): PromoBeacon-FIX` → phone conectou no SSID novo → tudo OK. Depois restaurei para **PromoBeacon** (verificado via serial + scan WiFi).

### Estado final do device
- Firmware commit **11555b1** (junto com 97acf75 do fix de reboot/factory-reset) + app **acb7ae8** (fix do protocolo 1-byte) — todos pushados em github.com/rafaelrogel/promobeacon
- Portal custom (313B) intacto no NVS; SSID = PromoBeacon
- Captura serial parada

### Pendência aberta (aguardando decisão do usuário)
Ofereci abrir issue no GitHub documentando o bug do live-update de SSID (referência) — usuário ainda não respondeu. Opção: só commit basta.
